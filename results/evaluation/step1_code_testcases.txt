**Prepared by:** Senior QA Engineer

### 1. Executive Summary
The `views_prescription.py` and `views_medtest.py` modules implement CRUD‑style endpoints for prescriptions and medical‑test uploads. The code works functionally, but a number of **security, data‑integrity, usability, and maintainability** concerns have been identified that could lead to:

| Category | Risk Level | Impact |
|----------|------------|--------|
| **Authorization bypass / data leakage** | High | Users can view, modify or “delete” records they do not own (e.g., a chemist can list every prescription). |
| **Mass Assignment / mutable POST hack** | Medium | Directly mutating `request.POST` may unintentionally allow clients to inject fields that are not intended to be set by the UI (e.g., changing `doctor` or `patient`). |
| **Timezone‑naïve dates** | Medium | Using `datetime.now()` / `datetime.today()` creates naïve datetime objects; they will be stored in UTC or local DB time depending on DB settings, causing inconsistent reporting. |
| **Missing validation on file uploads** | Medium | No size/type checks for `MedTestForm`; large or malicious files could be accepted. |
| **Error handling / exception swallowing** | Low | Broad `except Exception:` masks real errors and makes debugging harder. |
| **Potential CSRF exposure in delete flow** | Low | Deleting a prescription is done via a POST form, but the view does not explicitly enforce CSRF protection (relies on Django’s middleware). If the middleware is ever disabled, the endpoint is vulnerable. |
| **Inconsistent UX for form errors** | Low | The code manually clears `_errors` instead of letting Django handle them, which may hide validation messages from the user. |
| **Hard‑coded redirects** | Low | `HttpResponseRedirect('/prescription/list/')` and similar strings are brittle; using `reverse()` would be safer. |

Below is a detailed breakdown of each view, the associated risks, and a **test matrix** that you can use to verify that the defects are fixed.

## 5. Suggested Refactor (Pseudo‑code)

Below is a **concise example** of how the prescription `create_view` could be rewritten to address the top concerns:

```python
# views_prescription.py (refactored snippet)

from django.utils import timezone
from django.urls import reverse
from django.contrib import messages
from django.views.decorators.http import require_http_methods
from django.contrib.auth.decorators import login_required

@login_required
@require_http_methods(["GET", "POST"])
def create_view(request):
    # Only doctors may create prescriptions
    if not request.user.account.is_doctor:
        return HttpResponseRedirect(reverse('error:denied'))

    # Build initial data – never mutate request.POST
    initial = {
        'doctor': request.user.account.pk,
        'date': timezone.now().date().isoformat(),
    }

    if request.method == 'POST':
        form = PrescriptionForm(request.POST, initial=initial)
        if form.is_valid():
            # Force doctor field to the logged‑in user regardless of POST data
            prescription = form.save(commit=False)
            prescription.doctor = request.user.account
            prescription.save()
            logger.log(Action.ACTION_PRESCRIPTION,
                       'Prescription Created',
                       request.user.account)
            messages.success(request, "Successfully added the prescription.")
            return HttpResponseRedirect(reverse('prescription:list'))
    else:
        form = PrescriptionForm(initial=initial)

    # Disable doctor field for display purposes only
    form.disable_field('doctor')
    return render(request,
                  'virtualclinic/prescription/create.html',
                  {'form': form, 'form_button': "Add Prescription"})
```

*Key changes*:

* No mutation of `request.POST`.  
* `initial` data passed to the form.  
* Explicit role check with `is_doctor` property.  
* `messages` framework used for alerts (cleans session handling).  
* `reverse()` for redirects.  

Similar patterns can be applied to `list_view`, `update_view`, and the medical‑test views.

| **Exception handling** | `except Exception:` is used in every `get(pk=...)` block. | Over‑broad – masks DB‑layer errors (e.g., `DoesNotExist`, `MultipleObjectsReturned`, `DatabaseError`). Tests should verify the *right* error is handled and the user sees a helpful message. |
| **Missing response on error** | In `parse_speciality_delete` and `parse_symptom_delete` the `except` block only sets `template_data['alert_danger']` **and returns nothing**. | Django will fall through and return `None`, which triggers a **500 Internal Server Error**. QA must catch this as a critical defect. |
| **Logging** | `user_archive` has its logger line commented out (`#logger.log(...)`). | Inconsistent audit trail. The test suite should confirm that admin actions are logged for *all* mutating operations. |
| **Message wording** | `template_data['alert_danger'] = "Unable to delete the user. Please try again later"` (used in `restore_user`). | Copy‑paste error – the message refers to *deleting* when the operation is *restoring*. End‑users will be confused; a UI/UX test should flag it. |
| **Redirect URLs** | Hard‑coded strings like `'/admin/speciality/'`. | If URL patterns change, views break silently. Use `reverse('admin:speciality')` (or the name you gave the URL) – this also simplifies testing. |
| **CSRF protection** | Not visible in the snippet, but the views expect POST. | Ensure the corresponding templates include `{% csrf_token %}`; otherwise the POST will be rejected. |
| **Model‑level constraints** | Deleting a `Speciality` or `Symptom` may violate foreign‑key constraints (e.g., appointments referencing them). | The view currently catches *any* exception and hides the real cause. Tests need to verify the cascade or protect behaviour and that the user sees a meaningful message. |
| **Archive flag** | `user.archive = True` (soft delete) vs. actual `delete()`. | Business rule – confirm that archived users cannot log in and that `view_archived_users` only shows archived accounts. |
| **Import statements** | Unused imports: `sqlite3`, `sys`, `re`, `writer`, `QUOTE_MINIMAL`. | Clean‑up reduces noise and speeds up import time. Also, unused imports can hide missing dependencies in CI. |
| **Return type consistency** | Some branches return `HttpResponseRedirect`, others return nothing (see above). | Tests should assert that **every** execution path returns a proper `HttpResponse`. |

#### Sample pytest‑style snippet (U‑01)

```python
import pytest
from django.urls import reverse
from django.test import Client
from server.models import Account, Speciality, Action
from unittest.mock import patch

@pytest.fixture
def admin_client(db):
    admin = Account.objects.create_user(
        username='admin', password='pw', role=Account.ACCOUNT_ADMIN
    )
    client = Client()
    client.login(username='admin', password='pw')
    return client

@pytest.fixture
def speciality(db):
    return Speciality.objects.create(name='Dermatology')

def test_parse_speciality_delete_success(admin_client, speciality):
    pk = speciality.pk
    response = admin_client.post(
        '/admin/speciality/delete/',  # adjust to actual URL
        data={'delete': '1', 'pk': pk}
    )
    # 1️⃣ Redirect
    assert response.status_code == 302
    assert response.url == reverse('admin:speciality')
    # 2️⃣ Object gone
    with pytest.raises(Speciality.DoesNotExist):
        Speciality.objects.get(pk=pk)
    # 3️⃣ Log entry created
    assert Action.objects.filter(
        action=Action.ACTION_ADMIN,
        description='Speciality cancelled',
        performed_by__username='admin'
    ).exists()
```

### 2.3 Security / Pen‑Testing Checks  

| Check | Reason | How to verify |
|-------|--------|----------------|
| **Privilege escalation** | Ensure a non‑admin cannot reach these views via crafted URLs. | Try accessing each endpoint with a normal user; expect 302/403. |
| **Mass Assignment** | Verify that only the intended fields are written (e.g., `archive` flag). | Submit extra fields (e.g., `is_staff=True`) and confirm they are ignored. |
| **SQL Injection** | Though Django ORM escapes params, test with malicious `pk` values (`'1; DROP TABLE account;'`). | No error, object lookup fails gracefully. |
| **Information leakage** | The generic “Unable to delete the user. Please try again later” is fine; avoid stack traces. | Trigger an exception and confirm no traceback is shown to the client. |
| **Logging of sensitive data** | Ensure logger does **not** write passwords or PII. | Review log output after actions. |

## 3️⃣ REFACTORING RECOMMENDATIONS (to make QA easier)

1. **Return a proper response on every branch**  
   ```python
   except Speciality.DoesNotExist:
       template_data['alert_danger'] = "Speciality not found."
       return render(request, 'virtualclinic/admin/speciality.html', template_data)
   ```

2. **Narrow exception handling** – catch only what you expect:  
   ```python
   from django.core.exceptions import ObjectDoesNotExist
   try:
       speciality = Speciality.objects.get(pk=pk)
   except ObjectDoesNotExist:
       …
   ```

3. **Use `reverse` for redirects** – eliminates hard‑coded strings.  
   ```python
   from django.urls import reverse
   return HttpResponseRedirect(reverse('admin:speciality'))
   ```

4. **Log every mutating action** – uncomment or add the logger line in `user_archive`.  
   ```python
   logger.log(Action.ACTION_ADMIN, 'Admin archived a user', request.user.account)
   ```

5. **Extract common patterns** into a helper:  
   ```python
   def _handle_pk_lookup(request, model, pk_name='pk'):
       pk = request.POST.get(pk_name)
       try:
           return model.objects.get(pk=pk)
       except model.DoesNotExist:
           return None
   ```
   This reduces duplicated try/except blocks and makes mocking easier.

6. **Consistent messaging** – centralize alert strings in a constants module or use Django’s `messages` framework.

7. **Remove dead imports** – keep the file tidy (`sqlite3`, `sys`, `re`, `writer`, `QUOTE_MINIMAL`).

8. **Add type hints** – improves readability and static analysis (e.g., `def parse_symptom_delete(request: HttpRequest) -> HttpResponse:`).

9. **Add docstrings** describing each view’s purpose, expected POST keys, and side‑effects.
