### 1. IMPLEMENTATION GAPS  
**(Requirements that appear in the SRS‑based Suite A but are **not** exercised by the code‑based Suite B – i.e., the underlying functionality is missing or not testable from the current code base.)**

| # | SRS Requirement (Suite A) | Expected Behaviour (per SRS) | What is **missing** in the code (and therefore not covered by Suite B) |
|---|----------------------------|------------------------------|---------------------------------------------------------------------|
| 1 | **TC‑F‑01 – Patient Registration – Successful** | A new patient record is created, a confirmation UI message is shown, a session is started and a welcome e‑mail may be sent. | No *Patient* model / registration view / form exists in the supplied `models.py`. No API/endpoint to accept the registration payload, thus the whole end‑to‑end flow cannot be exercised. |
| 2 | **TC‑F‑02 – Patient Registration – Validation Errors** | Front‑end validation (required fields, email format, password length) blocks submission; server returns field‑level error messages; no DB record is created. | No validation logic (Model clean methods, serializers, or form validators) is present in the code base, so the negative‑path cannot be verified. |
| 3 | **TC‑F‑03 – Patient Registration – Duplicate Email** | System detects an e‑mail already in use and returns a “Email already registered” error; transaction is rolled back. | No unique constraint on a patient‑e‑mail field (or patient model at all) is defined; consequently the duplicate‑check cannot be performed. |
| 4 | **TC‑F‑04 – Admin – Add New Speciality** | Admin UI allows creation of a new *Speciality* row; DB table `Specialities` receives a new entry; the value becomes selectable for doctors. | Only the `Speciality` **model** exists; there is **no** admin view / form / API to create a record, nor any permission handling for “Admin”. |
| 5 | **TC‑F‑05 – Admin – Link Doctor to Speciality** | Admin can edit a doctor record and assign one or more specialities; the linkage is persisted and reflected in doctor‑search listings. | No `Doctor` model (or many‑to‑many relationship) is defined in the supplied code; consequently the linking operation cannot be coded or tested. |
| 6 | **TC‑F‑06 – Admin – Update Lab Details** *(excerpt only, but the SRS expects the ability to edit lab name, address, contact, etc.)* | Lab‑In‑Charge UI permits editing of lab information; changes are saved and visible to downstream processes. | No `Lab` or `LabInCharge` models, nor any related view/API, appear in the code base. |

> **Bottom‑line:** The code supplied for Suite B only contains a handful of **domain‑model** definitions (Speciality, Symptom, Location, Hospital). All **system‑level** business processes described in the SRS (registration, admin setup, doctor‑lab interactions) are absent, therefore they cannot be verified by the current test suite.

### 5. TOP 5 CRITICAL GAPS  
*(Ranked by the risk they pose to the Virtual Clinic’s ability to operate as a production‑grade healthcare system.)*  

1. **Patient Registration – Successful (TC‑F‑01)** – Without any registration endpoint or patient model, new users cannot join the system, halting the entire business flow.  
2. **Patient Registration – Duplicate Email (TC‑F‑03)** – Lack of a unique‑email constraint could allow duplicate patient identities, jeopardising data integrity and violating privacy regulations.  
3. **Admin – Link Doctor to Speciality (TC‑F‑05)** – Missing doctor‑speciality mapping prevents doctors from being discoverable for the right consultations, breaking core referral logic.  
4. **Admin – Add New Speciality (TC‑F‑04)** – If specialities cannot be created, the system cannot evolve to support new medical domains, limiting scalability.  
5. **Admin – Update Lab Details (TC‑F‑06)** – Absence of lab‑management functionality means diagnostic results cannot be routed correctly, undermining the clinical workflow.

---  

#### Quick Take‑away
- The **code base** currently implements only a **data‑model skeleton**; none of the **end‑to‑end business processes** stipulated in the SRS are present.  
- Conversely, the **model‑level features** (string representations, field limits, relationships) exercised by Suite B are **not documented** in the SRS test plan, indicating a mis‑alignment between requirements and implementation scope.  

**Recommendation:** Prioritise development of the missing functional layers (registration, admin UI/API, doctor‑lab linking) and augment the SRS‑based test suite to include model‑level checks, thereby achieving both **functional completeness** and **traceability**.
